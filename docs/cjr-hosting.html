Frappe CRM hosting

How our three self-hosted Frappe CRM sites are built, upgraded and backed up. This repo is the CRM fork they run.

Last updated 2026-10-29

Branch pins pull whatever is newest on that branch at build time, so Frappe usually moves up a v15 patch release on each rebuild.

Upgrading Pro Pack

  1. Read the release diff first: new patches, removed or retyped fields, and what the after_migrate hooks write.
  2. On the codingpro box, copy apps.json to apps.json.pre-<version>, set the crm_addons branch to the new tag, then run: 
    ./crm-upgrade.sh v1.84.0
    It takes a full backup with files to S3, stops the stack, builds (~15 min), checks every app and the Kanban patch are in the image, pushes to ECR, switches over and migrates.
  3. On each other site, back up first, because a redeploy does not: 
    docker exec crm_prod-backend-1 bench --site <site> backup --with-files
sudo /usr/local/bin/frappe-backup-sync.sh
./crm-upgrade.sh --redeploy <new tag>
  4. Check each site: bench list-apps, the lead count, new rows in Error Log, and /api/method/ping.

Rolling back

./crm-upgrade.sh --redeploy <previous tag>

Migrate only goes forward. If the release added tables or fields, also restore that site's pre-upgrade backup.

Changing the CRM itself

Our change lives on branch cjr/v1.84.0. For a new CRM release, rebase the patch onto the upstream tag, tag it v<version>-cjr, push, then run ./crm-upgrade.sh v<version>. The script refuses to build if the -cjr tag is missing.

Backups

  • The stack's cron container runs bench backup every hour (database and site config, no attachments).
  • A systemd timer on each box syncs them to the backup S3 bucket at :10 every hour, under a per-site prefix, and keeps two days locally.
  • Every upgrade takes a full backup with files first.

Adding a site

  1. Terraform: a new module that reuses the existing CRM product module. It creates the instance, an IAM role limited to ECR pull and its own backup prefix, and a DNS-only Cloudflare A record.
  2. On the box: Docker, 2 GB swap, AWS CLI, then pull the current tag from ECR.
  3. easy-install.py deploy with the four apps and an hourly backup schedule.
  4. Turn the scheduler on, generate the encryption key, restart the Python workers, add the backup timer, copy crm-upgrade.sh with the new SITE, and rotate the passwords.

Things that have bitten us

  • x86 only. The published Frappe images are amd64, so Graviton (t4g) fails with exec format error.
  • Server scripts need server_script_enabled in the global common_site_config.json. The per-site setting is ignored.
  • A new site starts with the scheduler off, and its workers can hold stale database connections until they are restarted.
  • The build stops the whole stack, even with --build-only.
  • Build cache: apps.json goes in as a BuildKit secret and is not part of the cache key, so the script clears the cache whenever the file changes.
  • Over SSH, pgrep -f crm-upgrade.sh matches its own command line. Use ps -eo args | grep "^/bin/bash ./crm[-]upgrade.sh".
  • No fixed IP on planto and meraki. A stop/start changes the IP, and re-applying Terraform points DNS at the new one.
  • Campaign email through Gmail SMTP stops once Gmail's sending limit is hit. Large sends need a slower rate or a dedicated sending service.
Credentials are never written here. Each box keeps its Administrator and database passwords in a mode-600 file in the home directory.
